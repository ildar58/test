# Дизайн: жизненный цикл записи V1 + мгновенный старт

Статус: согласовано (2026-06-02). Расширяет существующую реализацию
([recorder.ts](../sdk/src/recorder.ts), [auth.ts](../sdk/src/auth.ts),
[ingestion/src/server.ts](../ingestion/src/server.ts)), контракт — в
[ARCHITECTURE.md](ARCHITECTURE.md).

## 1. Цель

Формализовать **вариант 1** (сервис в auth-пути сам ставит cookie-флаги) и
убрать простой перед началом записи: сейчас после логина без перезагрузки
рекордер замечает маркер только на следующем опросе — **до 5 секунд**, и
действия в этом окне теряются. Цель — старт записи **сразу** после логина.

### Нефункциональные требования

- Старт записи после логина: **мгновенно** в Chromium; **≤1 с** в Safari/Firefox.
- Приложение (фронтенд) не модифицируем — рекордер инжектит прокси.
- Изменения аддитивны поверх текущего кода; правок немного.

### Вне области (отложено)

- **Вариант 2** (прокси сам детектит auth у нетронутого бэкенда).
- Поддержка `Authorization`-заголовка и токена в `localStorage`.
- Эти сценарии спроектированы отдельно (см. обсуждение auth-сигналов) и не
  входят в V1.

## 2. Топология (вариант 1)

Аутентификацией заведует **сервис записи**, через который проходит логин
(в демо это [ingestion](../ingestion); в проде — Go-сервис). Он же легитимно
ставит cookie. Прокси в auth-логику **не вмешивается**.

| Компонент | Ответственность |
|-----------|-----------------|
| **Proxy** (proxy-go/nginx) | инжект скрипта перед `</head>`; роутинг `/auth/*`, `/s/`, `/sessions`; раздача бандла `/_rec/`. Auth не трогает. |
| **Сервис** (ingestion → Go) | `/auth/login`/`/auth/logout` ставит/чистит cookie; `/s/` принимает батчи; хранит `session_id ↔ user`. |
| **SDK-скрипт** (бандл) | IDLE→ACTIVE по флагу, батчи на endpoint, стоп по исчезновению флага; читает `session_id` из cookie. |

## 3. Cookie-контракт

Все три ставит **сервис** в ответе `/auth/login`, чистит в `/auth/logout`.
Атрибуты: `Path=/; SameSite=Lax` (+ `Secure` в проде за HTTPS).

| Cookie | HttpOnly | Назначение |
|--------|:--:|------------|
| `session` | ✅ | секрет-токен; **авторизует** `/s/`. JS не читает. |
| `session_present` | ❌ | булев флаг присутствия сессии. Старт = появилась, конец = удалена. Одного ключа достаточно — отдельные «started»/«ended» не вводим. |
| `session_id` | ❌ | **server-minted** ID записи. Сервис маппит его в пользователя. |

Имя флаг-ключа и ID-ключа конфигурируемы (см. §6) — оператор может задать свои.

## 4. Мгновенный старт (без простоя)

Активацию определяет наблюдатель за маркером. Добавляем к опросу два мгновенных
триггера, всё — в бандле:

1. **`cookieStore.addEventListener('change', …)`** — событие при появлении/удалении
   cookie. Покрывает и старт (логин), и конец (logout).
2. **Опрос 1 с** как фолбэк для браузеров без `cookieStore` (Safari, Firefox).
   Снижаем интервал с 5000 → 1000 мс.
3. Существующие `focus`/`visibilitychange` оставляем.

Активация по ИЛИ любого триггера; на `start()` маркер читается синхронно — если
юзер уже залогинен на момент загрузки, запись стартует на t=0.

### Подтверждение (спайк на Chrome, 2026-06-02)

`cookieStore.change` срабатывает на cookie, выставленную **сервером** через
`Set-Cookie` (не только `cookieStore.set()`):

- логин (`Set-Cookie: session_present=1`) → `change` с `changed:['session_present']`
  через **~76 мс** (round-trip логина, не задержка события);
- logout (`Set-Cookie … Max-Age=0`) → `change` с `deleted:['session_present']`.

Допущение, на котором держится подход, проверено на реальном браузере.

## 5. Жизненный цикл

1. Первый рендер → прокси инжектит скрипт → рекордер в **IDLE**.
2. Логин (`fetch /auth/login` через прокси → сервис) → сервис ставит
   `session` + `session_present` + `session_id`.
3. Браузер сохраняет cookie → `cookieStore.change` (~76 мс) → рекордер
   **стартует сразу**: читает `session_id` из cookie, активирует rrweb, шлёт батчи.
4. `/s/`: сервис проверяет `session`-токен → пишет в `<session_id>.jsonl`,
   атрибутирует пользователю по `session_id ↔ user`.
5. Logout (`fetch /auth/logout`) → сервис чистит cookie → `cookieStore`
   `deleted` → рекордер флашит остаток и останавливается.
6. Перезагрузка залогиненного → cookie на месте → `start()` активирует
   мгновенно, та же запись продолжается (continuity бесплатно через cookie).

## 6. Изменения по компонентам

### SDK

- **[auth.ts](../sdk/src/auth.ts) `watchMarker`:** добавить подписку на
  `cookieStore.change` (если API есть) — в обработчике звать `check()`.
  Опрос и `focus`/`visibilitychange` сохранить как фолбэк.
- **[config.ts](../sdk/src/config.ts):** `markerPollMs` 5000 → **1000**; добавить
  `sessionIdCookieName` (дефолт `session_id`). `markerCookieName` уже есть.
- **[recorder.ts](../sdk/src/recorder.ts) `resumeOrCreateSessionId`:** вместо
  `crypto.randomUUID()` + sessionStorage читать `session_id` из cookie
  (`readMarker`-подобный геттер значения). Если cookie нет на момент активации —
  не активироваться (флаг и ID сервис ставит атомарно одним ответом, рассинхрон
  маловероятен; логируем и ждём следующего триггера). `batch_seq`-монотонность
  по-прежнему держим в sessionStorage.

### Сервис ([ingestion/src/server.ts](../ingestion/src/server.ts))

- **`/auth/login`:** помимо `session` и `session_present` сминтить
  `session_id=<uuid>`, положить в cookie (не HttpOnly), сохранить в записи
  сессии (`{ token, sessionId, username }`).
- **`/auth/logout`:** дополнительно очистить `session_id`.
- **`/s/`:** авторизация по `session`-токену (как сейчас); прочитать `session_id`
  из тела, сверить с `entry.sessionId` (анти-форж, т.к. ID не-HttpOnly), писать
  под этим ID, атрибутировать `entry.username`.

### Proxy ([proxy-go](../proxy-go), [nginx.conf](../proxy/nginx.conf))

- Инжект-сниппет передаёт конфиг в `init`, напр.
  `PamRecorder.init({ endpoint:"/s/", markerCookieName:"session_present", sessionIdCookieName:"session_id" })`
  (имена опций совпадают с полями `RecorderConfig`).
  Если значения дефолтные — сниппет можно оставить минимальным.
- **Прокси auth НЕ детектит и cookie НЕ ставит** — только инжект скрипта +
  роутинг (как сейчас). Перехват auth прокси (вариант 2) в V1 не делаем.
- Прочая логика прокси без изменений.

## 7. Server-minted `session_id` (смена поведения)

Сейчас `session_id` минтит **клиент** (`crypto.randomUUID`), а пользователь
резолвится по токену. Переносим минт ID на **сервис** (по концепции: «сервис
ставит ID сессии», «по ID определяю юзера»). Плюсы: единый серверный ID
записи+личности; reload-continuity бесплатно (cookie переживает перезагрузку),
клиенту не нужен sessionStorage для ID.

**Безопасность:** `session_id` не-HttpOnly → подделываем из JS. Поэтому он
**не** является ключом авторизации — `/s/` по-прежнему гейтится HttpOnly
`session`-токеном; `session_id` лишь именует поток записи и сверяется с записью
сессии на сервере.

## 8. Обработка ошибок

- **401 на `/s/`** (токен истёк/невалиден) → существующий cooldown
  ([recorder.ts](../sdk/src/recorder.ts)) сохраняем без изменений.
- **Нет `cookieStore`** (Safari/FF) → опрос 1 с; потолок задержки старта ≤1 с.
- **Сетевая ошибка батча** → текущее поведение (drop без ре-кью) сохраняем.
- **Нет `</head>`** для инъекции → прокси пропускает ответ как есть и логирует
  (proxy-go уже так делает).

## 9. Тестирование

- **Юнит (SDK):** `watchMarker` дёргает `onChange` через мок `cookieStore`
  (set → present, delete → absent) и через опрос; чтение `session_id` из cookie.
- **Юнит (сервис):** `/auth/login` ставит три cookie (`session_id` не-HttpOnly,
  непустой); `/s/` отвергает несовпадение `session_id` с записью сессии.
- **E2E (Playwright):** после логина запись стартует **< 200 мс** (нет 5-сек
  дыры); logout останавливает запись; перезагрузка продолжает ту же запись.

## 10. Допущения

- Браузерный парк преимущественно Chromium → `cookieStore` даёт честный ноль;
  Safari/FF получают ≤1 с (приемлемо, согласовано).
- Логин всегда проходит через сервис записи (предпосылка варианта 1).
